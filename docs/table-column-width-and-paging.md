# ElTable 列宽解析与分页

本次修复的三个问题都发生在「`ElTable` 在窄容器里被当表格用」这条路径上（`ElDropDownTableGrow` 的下拉面板是最小复现）。
记录在这里，避免以后再把它们当成 CSS 问题查。

## 1. 列宽解析：`Width` → `MinWidth` → **auto**，再在宽度之外加表头图标盒

`ElTable.razor` 的两个 `<colgroup>`（:102 表头、:291 表体，行号随批次漂移）现在统一调用 `ElTable.razor.cs` 里的 `ResolveColumnWidth(header)`：

| 优先级 | 来源 | 输出到 `<col width>` |
| --- | --- | --- |
| 1 | `TableHeader.Width`（`ElTableColumn.Width`） | 原样（如 `140`、`160px`、`30%`） |
| 2 | `TableHeader.MinWidth` | 去掉 `px` 后的整数，非法/<=0 则跳到第 3 档 |
| 3 | 都不写 | **`null` ⇒ 属性整个省略（auto 列）** |

**第 3 档是 2026-10-15 批次㊸ 改的**（推导、翻面读数与逐视口实测记在 `docs/table-auto-column-width.md`）：
改前这里兜底成 `80` 并写进属性，于是本仓**没有 auto 列**，而 `table-layout:fixed` 在「每列都带宽度、
声明和 < 表格宽度」时把富余**按声明宽度比例**摊给每一列 —— 钉死的宽度一个都保不住
（zyweb 部门维护表 `160/160/200/60` 在 1106px 容器里实测摊成 `305/305/381/114`，「操作列太宽」就是这么来的）。
现在不写宽度的列 `<col>` 不带属性 ⇒ 浏览器把**剩余宽度均分给 auto 列**，写了的列按声明钉死，
这一条与 Element Plus（不写 `width` 的那一列吃掉富余）对齐。

⚠️ auto ≠ 放弃可读性：`ColumnsTotalWidth` 仍按 `80 + 该列表头图标盒` 给 auto 列记账，
`TableWidthStyle` 的 `max(100%,Σ)` 因此照旧撑开表格，窄容器是**横向滚动**而不是把列压窄 ——
本篇 §1b 那条「逐字母竖排」的回归不会因为批次㊸ 而回来。

**第 4 步：上面解析出的"列宽本体"再叠一个表头图标盒加量**（`ElTable.razor.cs:991-1075`，2026-10-09 批次⑦补）：

| 表头部件 | 加量 | 依据 |
| --- | --- | --- |
| `Sortable`（`.caret-wrapper`） | `+24` | 库 CSS 给这个命中盒写死 `width:24px`（盒高批次⑧已按 EP 源码块改成 `14px`，本站实测 **24×14**；批次⑦当时是遗留的 24×34。加量只取宽度，与盒高无关） |
| `Filters` 非空 或 `AdvancedFilter`（漏斗触发器） | `+18` | 图标 12px + 本库 `margin-left:6px`；`transform:scale(.75)` 只缩视觉不缩布局盒 |
| 两者都有 | `+42` | 同一个列同时进两项 |
| 宽度是百分比（`"30%"`） | 不加 | `width` 属性写不了 `calc()`，硬拼数字会把百分比变成固定像素，原样透传 |
| auto 列（批次㊸） | 不加进属性 | 没有钉死的宽度可加；`+加量` 只进 `ColumnsTotalWidth` 的那份记账 |

口径来自用户两条纠正：「不是行高没撑开，这种的话，应该宽度自适应」、「如果设定了列宽…再设定了排序或过滤，
这 2 个是单独算的」⇒ **声明宽度是给文字的房间，图标盒算在这条宽度之外**。
本仓没有 EP 的 realWidth 布局引擎（列宽由 `<col width>` 直接钉死），若把图标算在声明宽度里面，
`Width="110"` 的「单价(元)」带排序时净宽只剩 66px（`110 − 20 pad − 24 caret`），表头文字必被 `.cell{overflow:hidden}` 裁。
加量同时进 `ColumnsTotalWidth` → `TableWidthStyle` 的求和，所以**宁可横向滚动也不压列**。
完整推导、800×700 视口下的逐列实测与翻面变异读数记在 `docs/table-header-cell-and-column-width.md` §2。

⚠️ 三个坑（都在批次⑦踩过）：
1. 表头渲染漏斗的 `@if` 与列宽的加量必须读**同一个** `HasFilterTrigger(header)`（`ElTable.razor.cs:1050`），
   分成两处写就又会"渲染了漏斗却没留宽度"。
2. `ElTableColumn.Width` 的类型是 **`string`**（`ElTableColumn.razor.cs:15`），`TableHeader.Width` 才是 `IntString?`
   （`TableHeader.cs:17`）—— bUnit 里传 `IntString`/`int` 会静默变 null，列于是走 auto（批次㊸ 之前是回落 80）。
3. 量列宽的几何断言必须建立在 `tableW == Σcol` 上（窄视口），否则 `table-layout:fixed` 会把富余按比例摊给每列，
   去掉加量照样撑得开，翻面断言恒绿＝探针空转。

### 1b. 为什么「无宽列」在窄容器里必须有那份 80px 记账

`.el-table__header { table-layout: fixed }`（index.css）。
`table-layout:fixed` 下 `<col width="auto">` 是**非法值**，浏览器当作「未指定宽度」处理 ——
剩余宽度按列**均分**，而不是按内容。10 个无宽度列挤在 302px 的表里就是每列 25px；
再叠加 `.el-table .cell { word-break: break-all }`，`Category` 被逐字母竖排成
`C/a/t/e/g/o/r/y`，整张表看起来就是「一堆斜着散的字母」。

批次㊸ 把「属性写 80」换成「记账算 80」之后，这一条仍然成立：表格的 `min-width` 按 Σ(含 auto 列 80) 撑开，
容器不够宽就出横向滚动条，均分出来的列宽下限 ≈80px。**要躲开的是「按内容收缩」，不是「按剩余空间均分」。**

## 2. 表宽：`width: max(100%, <列宽之和>px)`

`TableWidthStyle` 会把所有列宽（含选择列 55px；auto 列按 80+图标盒记账）求和后输出：

```csharp
Fit == true  → "width:100%;width:max(100%,{total}px)"
Fit == false → "min-width:100%;min-width:max(100%,{total}px)"
```

- 列宽之和 ≤ 容器时：`max()` 取 `100%`，与改造前**完全一致**（不引入额外滚动）。
- 列宽之和 > 容器时：表格保持真实宽度，`.el-table__body-wrapper` 自带的 `overflow-x:auto`
  横向滚动，表头由既有的 `SyncHeaderScrollAsync` 跟着走 —— 这正是 Element Plus 的行为
  （宁可横向滚动，也不把列压到不可读）。
- 先写一条老浏览器也能解析的声明，再写 `max()` 那条：不支持 `max()` 时忽略第二条，
  自动退回原来的 `100%` 行为，不会把布局打崩。

⚠️ **求和折像素要剥 `px` 后缀**（批次㊸ 修的第二个缺陷）：这里曾用 `int.TryParse(ResolveColumnWidth(header))`，
而宿主普遍写 `Width="160px"` ⇒ `TryParse` 失败、该列静默按 80 记账，整张表的 Σ 失真
（部门维护表真实 580px 记成 320px，页面读数 `max(100%,320px)`）。
现在走 `ParseColumnWidthPixels`（`ElTable.razor.cs:1178`）：剥 `px` 后再 `TryParse`，非法值才回落 80；
`<col width>` 的字面值保持宿主原样。百分比列返回 0 不参与像素求和。

⚠️ **百分比只能写在 `<col width>` 属性上、且浏览器实际忽略它**：试用四档实测
`Width="100%"` 与不写一样被当作未参与分配，全百分比时列塌成等宽 ——
所以「让某一列吃满剩余空间」的正解是**不写宽度**（auto 列），不是写 `100%`。

## 3. 显式 `<ElTableColumn />` 优先于反射自动列

`AutoGenerateColumns` 默认 `true`，而 `InitilizeHeaders()` 是在 `SetParametersAsync` 里调用的
—— 那时子组件（`ElTableColumn`）**还没注册**，`Headers` 是空的，于是反射列先生成；
子组件随后再往同一个 `Headers` 里追加，两套表头共存。

例：`<ElTable DataSource="MockData.Products">` + 4 个声明列，`Product` 有 7 个属性
→ 实际渲染 11 列（`Id/Name/Price/Stock/Category/OnSale/CreatedAt` 与 `名称/类别/单价(元)/库存` 同时存在）。

修复方式：自动生成的表头打上 `TableHeader.IsAutoGenerated = true`，
`AddColumn(ElTableColumn)` 在注册第一个显式列时把自动列整批丢掉。
`Ignore` 标记项与可编辑表格的「操作」列走同一条路径，不受影响。

## 4. 分页真正切片数据

改造前 `EnablePagination` 只是渲染了一个 `ElPagination`，表体循环 `for (i < rows.Count)`
永远渲染全部行 —— `PageSize=3` / `Total=6` 时页面显示 6 行、分页器却显示 2 页。

现在表体迭代 `PageRows`：

```csharp
EnablePagination && PageSize > 0 && rows.Count > PageSize
    ? rows.Skip((page - 1) * PageSize).Take(PageSize)
    : rows            // 行数不超过一页时原样返回，行为不变
```

当前页超出范围时按**最后一页**渲染（只夹取渲染用的局部变量，不写回 `CurrentPage` 参数）。

## 4b. 分页器总数回落本地行数（`EffectiveTotal`）

表体切片用 `rows.Count`，分页器却只读宿主的 `Total` 参数，而 `Total` 默认 0 且没有任何地方
按数据源回填（`ElTable.razor.cs` 里 `Total` 只有声明处）——本地数据不显式传 `Total` 时，
`Math.Ceiling(0 / PageSize) > 1` 恒假、`NoPaginationOnSinglePage` 又默认 true，于是
**12 行 / PageSize=3 的表格只渲染头 3 行，分页器整条不出现**，用户既看不到总数也翻不了页。

现在分页器读 `EffectiveTotal`：

```csharp
Total > 0 ? Total                 // 远程分页：宿主给的总条数优先
          : (树形 ? 顶层节点数 : rows.Count)   // 本地：与 PageRows 同一基数
```

`rows` 是**已应用筛选与排序**的集合（`ApplyFiltersAndSort` 末尾赋值），所以回落值跟着
筛后行数走，不会出现「筛完只剩 4 行、页码还按 200 条排」。远程分页宿主传了 `Total`
就维持原语义，未传者行为不变（回落恰好等于宿主本来该传的值）。
